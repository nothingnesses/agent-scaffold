## [Unreleased]

### Added

- Serialised reasons on the `status` and `next` `--json` projections (`src/main.rs`, `src/next.rs`), so a machine consumer can tell WHY a part is absent rather than reading the same bare `null` for every cause. `status`'s projection gains `metrics_absent_reason` beside `metrics`, and `next`'s gains the same field plus `resume_state_absent_reason` beside `resume_state`, while its `no_active_loop_reason` is retyped from an unserialised free string to a closed enum and now appears in the JSON. Each value is a closed kebab-case token: `log-absent` or `log-not-this-project` for the metrics half; `ledger-absent`, `no-resume-section` or `ledger-not-this-project` for the resume block; and `no-plan-steps`, `all-steps-terminal` or `metrics-not-this-project` for the active loop. Each field is always present, `null` when its part is present, matching the projections' existing no-omitted-field convention. Where an absent cause and an unpairable one both apply the unpairable one wins, since a bare absence is exactly the conflation the vocabulary exists to prevent, and the shared `not-this-project` spelling lets a consumer join `metrics_absent_reason` and `no_active_loop_reason` without a lookup table. The human text is unchanged for every cause that existed before.
- An `agent-scaffold audit` subcommand (`src/audit.rs`): an advisory, static code-value report of code that may not be earning its keep. It is projected from a typed intermediate, the `CodeValueReport`, whose `AuditRecord` is a closed enum (`DeadCode`, `UnusedDep`, `DeclaredReason`) carrying only each kind's own evidence, so a candidate verdict is derived at projection time rather than stored. Every report leads with a single-sourced mandatory caveat (a passing audit is necessary but not sufficient, and only relative to the named signal set), and a `generated_from` signal set records which signals ran so an absent signal widens the caveat rather than reading as a clean pass. `--json` prints the intermediate to stdout and writes no file; otherwise the Markdown report is written to `docs/plans/<task>.code-value-report.md` (or `--out`). It is read-mostly: it writes only its own report and never edits `src/`, `Cargo.toml`, the plan, or the metrics log, and never deletes anything; a human decides each candidate. This first increment ships the schema, the projection, and the caveat with an empty report; the signal harvests (rustc dead-code, the suppression-marker and FFI source scan, and `cargo-machete` unused dependencies) are later increments.
- A `type:"waiver"` instrumentation record and a W5 `validate --workflow` check (`src/metrics.rs`, `src/workflow.rs`, `pack/instrument.md`), one unified concept for an authorised exemption from the convergence bar. A waiver carries a `unit` (`step` or `increment`), the `step` slug (plus an `increment` token present exactly for an increment-unit waiver), a `reason` (`predates-logging`, `review-skipped`, or `accepted-at-escalation`), an `evidence_tier` (`self-declared` or `record-backed`), and an `evidence` pointer present exactly for the record-backed tier. W3 becomes convergence-OR-waiver: a `complete` step with no round records is exempt only when a step-unit waiver covers it, and an increment whose peak `consecutive_clean` is short of its risk class's required streak is exempt only when an increment-unit waiver names it, while a step with neither converging rounds nor a covering waiver still fails and a `risk_class`-inconsistency is never waived. The new W5 check keeps waivers honest, orthogonally to W3: every waiver names a real Roadmap step, an increment-unit waiver's `step` owns its `increment`, every record-backed waiver's `evidence` joins to a real `type:"escalation"` record with `human_decision:"decision"` that is scoped to the waived unit (so a self-declaration cannot cite an unrelated escalation to earn the strong tier), and the `reason` <-> `evidence_tier` pairing is enforced so a self-declaration cannot claim the strong tier. Best-effort `parse_waivers` and `parse_escalations` projections feed the checks, and a malformed waiver is reported by the strict schema check and dropped by the projection, so it can never silently grant an exemption. This is the second Q-44 structured-data pilot.
- A `type:"decision"` instrumentation record (the decision receipt), a `type:"baseline"` record declaring the historical-exemption cutoff, and a W4 `validate --workflow` check (`src/metrics.rs`, `src/workflow.rs`, `pack/instrument.md`). The decision record captures a human decision as `q_id`, the presented `options` (a non-empty string array), the `recommendation`, and the human's `chosen` option, with the validator enforcing that `chosen` is one of the presented `options` so the record is auditable evidence the options were shown rather than a self-certified flag. The baseline record declares a `questions_through` cutoff (a `Q-<n>` id) that names the last Open-Questions item predating the mechanism. Best-effort `parse_decisions` and `parse_baseline` projections feed W4, which requires a matching receipt for every `decided -> folded into <slug>` Open-Questions item whose id index is strictly after the declared cutoff, so the historical decided items at or below the cutoff are exempt while later ones are checked. The cutoff is an independent declared value, not derived from the receipt set, so a forgotten receipt cannot move its own exemption boundary; when no baseline is declared, every decided item requires a receipt.
- `validate --workflow` cross-references a plan's Roadmap against the round log (`src/workflow.rs`): every Roadmap step marked `complete` must have converging round records, so a step marked done without its review loop, or one that never reached the clean-round streak its risk class requires, is reported. It reuses the same metrics log as the rest of `validate`.
- Two Roadmap statuses, `trivial` and `grandfathered`, terminal complete-like statuses that declared a step's review history so the workflow cross-reference did not flag it. RETIRED in the same unreleased cycle: their review-exemption is now carried by the unified `type:"waiver"` record above, so a step that predates round-logging or whose review was skipped is marked `complete` with a covering waiver rather than given a special-case status. `skipped` stays a distinct status.
- An optional `harness` field on each `reviewers[]` entry in the instrumentation `round` record, naming the CLI a reviewer ran on (for example `claude-code`, `codex`, or `gemini-cli`), so per-reviewer calibration can distinguish harnesses, not just models. It is optional and validated as a string only when present, so existing round records stay valid.
- Optional module `isolation` (`--module isolation`): a guidance-only module that wires a project to the external agent-box and agent-images projects for container/worktree writer-agent isolation. It renders setup pointers into `AGENTS.md`'s `{{modules}}` block (install an agent-images image, create the global `~/.agent-box.toml`, spawn writers via `ab new`/`ab spawn --git`) as the concrete form of the container tier the Writer isolation rule names. It drops no files into the project tree, takes no runtime dependency on those projects, and reimplements no isolation.
- Optional modules: a `--module <name>` selection scaffolds an opt-in bundle on top of the core pack. A `{{modules}}` render slot concatenates each enabled module's guidance into `AGENTS.md` (empty and byte-identical when no module is selected), and a module may declare `requires` to auto-enable its dependencies. Asset manifests gain a `module` tag and an `executable` field (drop a file with its executable bit set). The first module is `checks` (`--module checks`): a deterministic verification gate that scaffolds a user-owned `.agents/checks.toml` (flat `[[check]]` entries with a `command`, a `kind` of `lint`/`format`/`test`/`mutation`, an optional non-mutating `check` command, and optional `paths` globs), a seeded `ast-grep` config plus example rule, a read-only `checks-reviewer` role prompt, and a pre-commit hook. The `agent-scaffold checks [--staged]` subcommand reads `checks.toml` and runs the lint and format checks inside a throwaway git worktree, so an in-place formatter can never mutate the live tree (`--staged` isolates the index content for hook use). `scaffold --module checks --with-precommit-hook` installs a git pre-commit hook create-if-absent (only when the resolved hooks dir is inside the scaffolded project, never clobbering an existing hook).

### Changed

- `validate --workflow` now FAILS when it cannot see a round log, where it previously announced a skip on stderr and exited 0 (`src/main.rs`). Asking for the workflow check and getting exit 0 from a check that never ran is a false green: a CI gate reads the exit status and not the stderr log, so the gate recorded a pass for a project with no machine enforcement of any workflow invariant. With no round log at the resolved metrics path the run now reports a problem naming that path and exits non-zero, whether the path came from the anchored default or from an explicit `--metrics`, and whether the plan came from a TOML-primary `--source` or a Markdown `--plan`. THE POPULATION THIS BREAKS is every project with no round log at the resolved path, which every project scaffolded without `--instrument` remains: such a project has the guidance tier of the workflow and not the deterministic one, and `validate --workflow` now says so rather than passing. The scaffolded `AGENTS.md` carries the same boundary on the sentence that promises the backstop, so a reader of that sentence can predict the exit code. Plain `validate`, including `validate --source` and `validate --plan` without `--workflow`, is unchanged: an absent log stays a stderr note at exit 0, because nobody asked for the check there. One further case changes its answer for the same reason: a bare `--source` filename run from inside `docs/plans` has no parents to derive a root from, so it looks for a log beneath `docs/plans` and finds none, which was a note at exit 0 and is now this failure naming the path it looked for.
- `validate --workflow` now REFUSES a round log it cannot attribute to the plan it is checking, and `status`, `next` and `status --resume` LEAVE OUT the part they cannot vouch for instead of projecting it (`src/main.rs`, `src/next.rs`). Anchoring the default `--metrics` to the plan source (above) fixed where the DEFAULT log resolves and did nothing about a log named explicitly, so a second rule sits on top of it: where a command READS a plan, the artifact it is about to read must live under that plan's project root, resolved through both files' real on-disk locations so a symlinked plan cannot be passed off as belonging to its neighbours. Where no plan is read at all, which is always so for `status --resume` and is so for `status` and `next` whenever neither a TOML-primary `--source` nor a readable `--plan` resolves, those three take their roots from the anchors instead: every `--source` or `--plan` supplied THAT IS ON DISK yields one and the artifact must be under all of them. An anchor that is not on disk yields a root only when no supplied anchor is on disk, derived from the path itself resolved as far as the filesystem allows, and a `note:` on stderr reports that the anchor is not there, so a typo is visible rather than silent while what the anchor's own directory owns is still read. Beside an anchor that IS on disk it yields no root and the one on disk decides, so a `--plan` naming a file that has not been written does not withhold the `--source` project's own log and ledger. ON DISK means the existence check answered yes: an anchor the check cannot answer for at all (a directory above it the process cannot traverse, a symlink loop, a name the kernel rejects) is grouped with the anchors that are not on disk rather than with the ones that are, so a path the tool could not check never becomes the one that decides, and its `note:` says the check failed rather than that the path is missing. With NEITHER anchor there is nothing to pair against, so no root is derived, no check fires, and the current-directory-relative defaults stand. `validate --workflow` has no such fallback and needs none: with no plan resolved it has nothing to check and refuses on that ground without reaching containment. The root comes from the plan being CHECKED rather than from the anchor the log was derived from, which is what lets it reach a `--source` in one project paired with a `--plan` in another; the resolved log is always under the anchor's root, so an anchor-rooted rule could never have caught that pairing. The two commands answer the same question differently on purpose. `validate --workflow` reports a problem naming the plan, the log, the derived root and what to do about it, and exits non-zero without running the check. `status` and `next` still EXIT 0: `status` prints `metrics: unavailable, <why>` in place of the record count, `next` withholds the count and the WHOLE `ACTIVE LOOP` block rather than deriving an instruction from evidence it cannot vouch for, and `status --resume` prints a note naming the rejected ledger instead of the `## RESUME STATE` block. TWO BREAKS TO KNOW ABOUT. A setup that deliberately points one project's `--metrics` at a log outside that project's own root now exits non-zero under `--workflow`. And a layout in which `docs/plans` or `docs/metrics` is a symlink that lands the plan and the log under different real roots is now refused by `validate --workflow` and omitted by the projections, even though it worked before; the trade taken is that a loud refusal beats silently reading the wrong file. The rule is containment, not project identity: a foreign log copied INSIDE the plan's own tree is still indistinguishable from the plan's own, because a round record carries no project of its own to check.
- The metrics log and the review ledger are resolved from the PLAN SOURCE rather than from the process working directory, on `validate`, `status` and `next` (`src/main.rs`). With no `--metrics`, the log is `docs/metrics/workflow.jsonl` under the project root derived from the plan source (the nearest `<root>/docs/plans/` ancestor of `--source`, else of `--plan`, else the source's own directory when it has no such ancestor), and the ledger `next` and `status --resume` read is `<task>.ledger.md` beside that source. Previously both defaults were relative to the current directory, so pointing any of these commands at a plan in another project joined that plan to THIS directory's log and ledger: `validate --workflow` could report `workflow invariants hold` for a plan with no review evidence of its own (the round log joins a step by slug alone, so a borrowed slug was enough), `next` could emit a confident `mark the step complete` instruction derived from another project's rounds, `status` could report another project's record count, and `status --resume` could print one project's `## RESUME STATE` block as another project's resume anchor. A run made from the plan's own project root with a bare relative `--source`, the normal invocation, is unchanged and still prints the relative paths it always did; the derivation is textual and consults no VCS. An explicit `--metrics` or `--ledger-fragment` is still used verbatim, and a run with neither `--source` nor `--plan` has nothing to anchor to and keeps the current-directory-relative paths.
- Hardened the scaffolded workflow guidance (`AGENTS.md` and the role prompts) after a design review. The review ledger and orchestrator round state move to a file committed beside its plan, so the workflow survives the orchestrator losing context and resumes across machines and sessions; the orchestrator follows an explicit per-round procedure to append the ledger and increment or reset the clean-round count. Convergence now requires consecutive clean rounds scaled to the stakes, and a review loop escalates to a human when the total rounds on an artifact reach the total-round cap (default five). A dismissed high-severity finding is re-checked by a second independent triager. The acceptance review gains a triager, matching the other review phases. A human interrupt now goes through a bounded intake assessment that advises on impact and gives feedback on the request, routing trivial requests directly and non-trivial ones through the plan.
- Split the review and triage steps into separate nodes in the README workflow diagram, so the triager owns the convergence decision.
- Generalised the reviewer and explorer diversity guidance in `AGENTS.md` from "different models where available" to "different models or harnesses where available", so a user running more than one CLI is guided to spread reviewers across harnesses too, and extended the review-request prompt's depth cue to match.

## [0.0.1] - 2026-07-10

### Added

- Initial release. Scaffolds a repeatable agent workflow into a project: a canonical, harness-agnostic `AGENTS.md`, a planning-document template under `docs/plans/`, reusable per-role prompts, and a selectable set of engineering principles.
- Principle selection. `--principles` accepts `default`, `all`, `none`, a comma-separated list of ids, and `tag:<t>` tokens; `--principle-detail` (`name`, `summary`, or `full`) sets the rendered detail, and `--list-principles` prints the selection.
- Interactive two-pane selector (ratatui), the default on a terminal: toggle inclusion, reorder, filter by name/id/tag, undo and redo, and a save-confirmation modal.
- Write safety. A run previews a plan and writes only with `--write` or the selector's Save confirmation; `--dry-run` previews explicitly. Two-tier ownership refreshes tool-owned reference assets under `.agents/` and creates user working files only if absent, unless `--force`.
- Bring-your-own packs. `--template <dir>` scaffolds from a user-supplied pack via a `pack.toml` manifest (`[[asset]]` and `[[var]]` entries), with `--var key=value` substitution and pack-owned principles.
- Version control. Initialises a git repository by default (`--vcs git|none`), skipped when the target is already inside a repository.
- Runs without Nix as a standalone binary (Rust 1.88 or newer).
