### `prompt-drift-guard`: extend the whole-file drift guard to the deployed prompt copies

Not started. This is an ENFORCEMENT change in `src/`, not a prose change, and it closes a verified gap rather than settling a design question, so it carries no `[[question]]` and no receipt.

The gap, verified directly rather than taken from the review. `src/agents_md_drift.rs` is the whole-file drift guard, and it covers exactly two files: it embeds `../AGENTS.md` and `../.agents/AGENTS.reference.md` with `include_str!` and compares each against a fresh render of the built-in pack. A sweep of every `include_str!` in `src/` (`recommendation_rule.rs`, `agents_md_drift.rs`, `workflow_spec.rs`, `isolation_policy.rs`, `findings_naming.rs`, `pack.rs`, `plan/source.rs`, `plan/render.rs`, `metrics.rs`) shows that no test embeds or compares any file under `.agents/prompts/`. Those seven prompt copies appear only as destination strings in the scaffolded-asset list (`src/manifest.rs`, the `.agents/prompts/*.md` entries), which asserts WHAT the scaffold emits, never that the COMMITTED copy still matches it. So editing a `pack/prompts/*.md` file and forgetting to regenerate ships a stale deployed prompt and every check stays green. Three review agents reached this independently on step 90's plan review, and step 90 is itself an instance of the exposure: it edits three passages in `pack/prompts/orchestrator.md`, the file that carries most of that change and none of the enforcement.

What the guard must catch (the acceptance-shaped statement for this step):

- Editing any `pack/prompts/<role>.md` without regenerating the deployed `.agents/prompts/<role>.md` MUST fail `cargo test`, with a message naming the file and telling the reader to regenerate.
- A hand edit made directly to a committed `.agents/prompts/<role>.md`, with the pack left alone, MUST also fail. The guard is a two-way correspondence check, not a one-way staleness check.
- An incidental prettier reflow of a committed copy MUST NOT fail, on the same terms the existing guard already accepts for `AGENTS.md` (see the normalisation note below).
- The failure must be demonstrated, not asserted: per the now-live reproducible-evidence rule (`Q-66`, step 88), the implementer breaks the correspondence deliberately (edit one pack prompt, leave the deployed copy stale) and shows the new test fails, then reverts. A guard that cannot be shown to fail is not evidence of anything (plan Principle 6, "Ground decisions in evidence"; the AGENTS.md workflow guidance "Tests must actually exercise the code they claim to").

Reuse, do not reinvent. The existing guard already solved the two hard parts, and both apply unchanged here:

- PRETTIER NORMALISATION. The committed files are `prettier(render output)` because `just scaffold-self` runs the render and then `nix fmt`, whose prettier owns Markdown wrapping at `proseWrap=never`. A raw byte compare would fail on formatter reflow rather than on real drift, so the existing guard passes both sides through `normalize_wrapping` before comparing. The prompt copies live under the same formatter, so the new coverage must use the same normalisation rather than a byte compare.
- THE PRECONDITION FAIL-SAFE (the pattern step 80 established, and the part most likely to be skipped). `normalize_wrapping` is only safe while the guarded text contains no whitespace-significant construct, because it collapses whitespace runs; `assert_no_unprotected_construct` asserts that precondition on BOTH sides and fails loudly the day a nested list, indented code, or a multi-space inline span enters a guarded file, converting a latent masking bug into a visible failure. Any newly guarded file must be run through the same precondition assertion, not just the equality check. Check this against the actual prompt files early: if a prompt already contains such a construct, the precondition will trip immediately, and the answer is to harden `normalize_wrapping` (or exempt that construct deliberately), NOT to drop the assertion.

Implementation choice, decided here rather than left to the implementer. `include_str!` needs a literal path, so covering seven files by the existing pattern means seven more constants and seven more comparisons, which is the enumerated form, and it drifts the moment an eighth prompt is added to the pack. Prefer instead to DERIVE the guarded set from the manifest: render the self-scaffold asset set once, keep every asset whose `dest` starts with `.agents/prompts/`, and compare each against the committed file read from `CARGO_MANIFEST_DIR`. That makes adding a prompt to the pack automatically guarded, which is the one-source-of-truth form (plan Principle 8, and the AGENTS.md workflow guidance "One source of truth") and is why it is preferred over the smaller enumerated diff (plan Principle 1, "Prefer the cleaner long-term architecture over the smallest diff"). The trade-off to accept knowingly: reading at test time from `CARGO_MANIFEST_DIR` is slightly less hermetic than a compile-time `include_str!`, since it reads the working tree rather than a snapshot compiled into the binary. That is acceptable for a repo-local drift guard whose whole purpose is to inspect the working tree, and the existing guard is already repo-local in the same sense. If the implementer finds a concrete reason this does not hold, it is an impasse to raise, not to route around silently.

Scope boundary. Cover `.agents/prompts/` only. The same gap exists for the other copied assets the self-scaffold emits (`.agents/user-prompts/*`, `.agents/LEDGER.template.md`, `.agents/principles.toml`, `.agents/workflow.toml`), and if the derived-from-manifest form above is taken, widening the filter to cover them later is close to free. Do NOT widen it in this step without a human call (the AGENTS.md workflow guidance "No silent scope expansion"); note it in the step's report so the human can decide whether a follow-up is worth it. One asset that must NOT be guarded by this step: `.agents/prompts/checks-reviewer.md` is module-gated (`src/manifest.rs`, emitted only under `--module checks`), and the self-scaffold config the justfile pins uses no modules, so a fresh render under that config does not produce it. A guard that expects it would fail on a correct tree.

Documentation impact. Source and tests only. The step adds no scaffolded content, so no deployed file goes stale and no regeneration is required, which is the reason it can land independently of steps 90 and 91. Worth a CHANGELOG line if the project's convention covers test-only changes; check what `decision-receipt` and `waiver-model` did before assuming either way.

Interaction with steps 90 and 91. This step does not block either of them and neither blocks it. Landing it FIRST would mean step 90's regeneration of `.agents/prompts/orchestrator.md` is enforced rather than trusted, which is the better ordering on the merits; the order given (90, then 91, then 92) reflects that step 90 is already reviewed and in flight, not a judgement that the guard matters less. If the human wants the enforcement first, reordering costs nothing, since the two touch disjoint files.
