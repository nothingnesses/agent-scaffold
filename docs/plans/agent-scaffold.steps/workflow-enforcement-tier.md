Four defects, one family. ## Defect A, the false green (`Q-55` proper)

Run from INSIDE the fixture:

```sh
cd "$SCRATCH"
agent-scaffold validate --source docs/plans/TEMPLATE.plan.toml --workflow
```

Observed, with the streams separated:

```
stdout: docs/plans/TEMPLATE.plan.toml: 1 steps, 0 questions, valid
stderr: no metrics log at docs/metrics/workflow.jsonl; nothing to validate
stderr: --workflow has a plan source but the metrics log is missing; skipping the workflow check
exit:   0
```

CORRECTION TO `Q-55`'S OWN WORDING, which the implementer should not carry forward. `Q-55` says `validate --workflow` "silently passes". That WAS an OVERSTATEMENT: the skip WAS announced, twice, both in `src/main.rs:run_validate` (the `no metrics log at <path>; nothing to validate` note, and the `--workflow has a plan source but the metrics log is missing; skipping the workflow check` note that inc3 replaced with a reported problem). The correction is sharper than it first looks, because both announcements WENT to STDERR (both WERE `eprintln!`), while the only thing on stdout WAS the ok summary. The operative defect WAS therefore the EXIT CODE and nothing else: a CI gate reads the exit status, not the stderr log, so `validate --workflow` RETURNED success for a project with zero machine enforcement of any workflow invariant. Write it up as a false green, never as a silent one. Explorer B captured the streams separately at the pre-change build and confirmed stderr empty on the defect-B invocation and non-empty here, which is what makes the distinction measured rather than asserted.

THE MECHANISM. The `--workflow` block is a four-arm `match` in `src/main.rs:run_validate` over `(toml_primary, &plan_contents, &metrics_contents)`. The arm that FIRED here WAS that match's `_` catch-all, which PRINTED the skip note and PUSHED NO problem, so `problems` STAYED empty and `run_validate` TOOK its `if problems.is_empty()` success branch.

THE DECIDED REMEDY (human, 2026-07-31, receipt `q_id:"Q-55"`): FAIL WHEN `--workflow` CANNOT RUN. When `--workflow` is explicitly requested and no metrics log exists at the resolved path, the run exits non-zero and reports why. Plain `validate` (and `validate --source` / `--plan` without `--workflow`) is UNAFFECTED: an absent log there stays a stderr note and exit 0, because nobody asked for the check. The reasoning the human accepted: the user explicitly asked for the workflow check, so skipping it and reporting success is the defect. The policy applies to the resolved metrics path however it was resolved, whether from the anchored default or from an explicit `--metrics` value; "the user named a path that does not exist" is not a weaker case than "the default path does not exist".

WHAT WAS REJECTED, AND WHY. Make round-logging CORE rather than opt-in: rejected as forcing instrumentation on users who did not ask for it, and a substantially bigger change than the defect warrants (Minimal by default; the `--instrument` opt-in is the two-tier design working as intended, not the bug). Warn but keep exit 0: rejected because a warning with exit 0 is still green in CI, which is the actual failure mode being fixed; it would leave the defect in place and add a message beside it.

THE PRECEDENT THIS FOLLOWS, ALREADY IN THE TREE, so this is closing the second half of a hole whose first half is already closed. The sibling `(None, None, _)` arm of `src/main.rs:run_validate`'s `--workflow` match handles "`--workflow` requested but no plan source resolved" and pushes a hard problem, with the comment stating the identical reasoning: "`--workflow` was explicitly requested, so skipping would green-pass while checking nothing; make it a hard problem instead." That arm was itself a false-green fix (Inc 6, finding M-1) and is pinned by `tests/validate_workflow_toml_source_needs_no_plan.rs:127-171`. Defect A is the same defect on the other input, and the fix is the same shape.

A CASE THAT IS NOT PART OF THIS, named so the work does not creep into it. A metrics log that is PRESENT but EMPTY is not a false green and needs no change: the check runs, and W3 fails on any `complete` step with no round records (demonstrated in the acceptance check below). The missing-file case is different in kind because the check does not run at all.

THE REQUIRED END PROPERTY, which is what "done" means for this half regardless of the mechanism: `validate --workflow` must never pair a plan source with a metrics log belonging to a different project and report success. Where the tool cannot establish that the two belong together, it must say so and exit non-zero rather than proceed. A run made from the plan's own project root with a bare relative `--source`, which is the normal invocation, must be unchanged (Safe on existing projects), except for the symlink divergence recorded below as accepted cost (ii).

THE DESIGN PASS'S SHARPEST RESULT ON THIS POINT, and the reason the mechanism is anchor PLUS refusal rather than anchor alone: explorer A finished building the anchor and then attacked its own build, producing TWO FURTHER false passes against it, one with an explicit RELATIVE `--metrics` and one through a SYMLINKED plan source, both printing `workflow invariants hold` at exit 0 for a foreign project with no review evidence. ## The mechanism, decided rather than chosen here

`Q-55-mechanism` (human, 2026-07-31, receipt `q_id:"Q-55-mechanism"`): ANCHOR PLUS REFUSAL, IDENTITY QUEUED. Ship candidate (a), the metrics path anchored to the plan source, PLUS a refusal for unsafe pairings, covering `validate`, `next`, `status` and the ledger path, and QUEUE project identity in the round record to the validation-constraints step. The human declined both the wider option (identity fields in the same step) and the narrower one (anchor only). The recorded reasoning: the pass measured that anchoring alone leaves the DEFECT CLASS open, so the refusal is not gold-plating, while pulling identity in would edit the record schema that W3, W4 and W5 all read, which the calibration close already argued should be ONE deliberate edit rather than a rider on a path fix.

The implementer does NOT re-open any of the following. Each is recorded with the measurement that settled it.

DISTINGUISHING A DEFAULTED `--metrics` FROM AN EXPLICIT ONE: use `Option<PathBuf>` with a bare `#[arg(long)]`, and apply the default after resolution. Do NOT use clap's `ArgMatches::value_source`. The reason is NOT the 17 lines saved. Explorer A built both routes to a working state and then FORCED the `value_source` failure mode by renaming the argument id, simulating a later field rename. Both the subcommand and the argument are addressed by STRING, so in a DEBUG build clap panics (`` `"metrics_typo"` is not an id of an argument or a group ``, exit 101) while in a RELEASE build the same code silently answers "not supplied", so the user's explicit `--metrics docs/metrics/workflow.jsonl` is IGNORED and a different file is read with no message. That is a debug/release behaviour divergence, guarded only by clap's `debug_assertions`, in the code path whose entire purpose is deciding which file to read: the same self-concealing class as the defect under repair, which is what makes it disqualifying rather than merely uglier. Two lesser measured costs: `value_source` is `+96/-13` against `Option<PathBuf>`'s `+79/-15` for identical behaviour, and clap prints the `default_value` it was given with no way to keep the value and suppress the display, so `--help` would carry a now-false `[default: docs/metrics/workflow.jsonl]`. This independently vindicates Make illegal states unrepresentable, which A was told to TEST rather than repeat.

THE DERIVATION: a purely LEXICAL, NEAREST-WINS upward search. Start at the source's parent directory and walk up; the first ancestor whose own file name is `plans` and whose parent's file name is `docs` identifies `<root>/docs/plans`, and the root is that ancestor's grandparent. No filesystem access and no canonicalisation. The metrics default is then `<root>/docs/metrics/workflow.jsonl`. With neither a `--source` nor a `--plan` there is nothing to anchor to, so the historical CWD-relative path stands unchanged.

THE CONVENTIONLESS CASE, decided by `Q-55-noconvention` (receipt `q_id:"Q-55-noconvention"`): when no `docs/plans`-shaped ancestor exists, FALL BACK TO THE SOURCE'S OWN DIRECTORY, with the containment refusal layered on top. Chosen over a hard error. A had MEASURED the fallback resolving the `--source myplan.plan.toml`-at-a-repository-root case correctly, both from that root and from elsewhere, and Safe on existing projects favours resolving a legitimate layout over rejecting it. This is the case the first planner pass called "no convention to lean on"; there is one, and it is the same answer the CWD-relative default would have given from the right directory.

WHAT THE DERIVATION WAS MEASURED AGAINST. A built a case matrix in which every candidate log location carries a DIFFERENT record count, so the printed count identifies which file was actually read, then ran it. The `docs/plans` convention resolves correctly in every spelling constructed: absolute, relative, `./`-prefixed, and with a `..` that stays below the project's own `docs/plans` (that last works because `Path::file_name` returns `None` for a `..` component, so the walk skips past it and reaches that project's `docs/plans` above it). A plan at a root with no `docs/plans` resolves through the fallback. A subdirectory under `docs/plans` resolves to the project root. The rule never consults `.git`, so a nested repository and a directory outside any repository behave identically and correctly; "project root" here is a FILENAME CONVENTION, not a VCS fact, which is a feature (no VCS dependency, works in a tarball) and should be written up as one. ONE CASE IS A JUDGEMENT CALL AND IS RECORDED AS SUCH: a second `docs/plans` in the parent chain resolves NEAREST-WINS to the inner project. A chose it on the reasoning that the innermost project owns the plan, and reported it as "the only place I chose between two defensible answers without external evidence". It is not evidenced; an implementer or reviewer may revisit it on evidence, and must not treat it as settled by measurement. NOT IN THAT MATRIX, AND MEASURED AT WORK REVIEW: a `..` that climbs OUT through a `docs/plans` matches THAT directory, so `<root>/docs/plans/../../other/p.plan.toml` and `<root>/other/p.plan.toml` are the same file read against two different logs. It follows from the lexical rule rather than being a defect in it, it is not a regression (before anchoring, both spellings read the current directory's log), and it is the canonical guard in inc2, whose root comes from the REAL (canonicalised) location of the plan the check reads, which in that spelling is the source itself, that rejects it.

THE REFUSAL (candidate (b), layered on top). Before the four-arm match in `run_validate`'s `--workflow` block, derive the root from the REAL (canonicalised) location of THE PLAN THE CHECK READS, which is available BEFORE the match and does not force the guard down into the arms (the `toml_primary` binding is made above the match and `args.plan` is its fallback), resolve the metrics path by absolutising and canonicalising its longest existing ancestor, the path itself when it exists, and re-appending the components below it (so a log whose leaf does not exist yet still has its directory prefix resolved), and push a problem when the resolved log is not under that root. Where NO plan is read there is no root, so the predicate did not fire and every surface behaved as it did then, which is the answer the no-anchor case above already gets; on `validate --workflow` that case is the match's own `(None, None, _)` arm, already a hard problem for its own reason. A's measured message shape, which reports both paths and the root and tells the user what to do: "`--workflow` would join <source> against <metrics>, which is not under the plan's project root <root>; pass a `--metrics` under that root, or run against the plan's own log". Measured to close both of A's self-found false passes and to resist a `..` escape that climbs out of a fixture root to reach agent-scaffold's own 235-record log. TWO ADJUSTMENTS TO THAT SHAPE FOLLOW FROM THE ROOT DECISION BELOW AND ARE SPECIFIED HERE RATHER THAN MEASURED, because A's build could not tell the two files apart: the first slot names THE PLAN THE CHECK READS, which in A's build was the `--source` and is not always, and the remedy gains a third member for the case where the log was anchored on a different file than the checked plan, "or correct the `--source` and `--plan` pair", since neither of A's two remedies names that cause.

WHY THE ROOT COMES FROM THE CHECKED PLAN AND NOT FROM THE ANCHOR (human, 2026-08-02, receipt `q_id:"Q-55-endproperty"`, ROOT ON THE PLAN THE CHECK READS). The two are not the same file, and the gap between them was MEASURED AT WORK REVIEW on inc1: `resolve_metrics_path` anchors on `--source` first and `--plan` second, while the `--workflow` check reads a TOML-primary `--source` else the Markdown `--plan`, so a Markdown-primary `--source` in one project paired with a `--plan` in another was checked against the FIRST project's log and reported `workflow invariants hold` at exit 0 for a step with no round record of its own. The resolved log is DERIVED from the anchor, so it is always under the anchor's root and a predicate rooted THERE can never fire on that pairing; rooted on the anchor, the END PROPERTY above would have been met by no increment of this step, which is what forced a decision rather than leaving the rooting to the implementer. Three things the implementer should carry. It is ONE predicate and not two conditions layered: is the log I am about to read under the root of the plan I am about to check. In TOML-primary mode the checked plan IS the anchor and the rule is unchanged there; it differs only when a `--source` is given and is not TOML-primary. And it covers the TYPO'D `--source`, a nonexistent `--source` beside a readable `--plan`, where the root comes from the plan that WAS read while the log still comes from the lexical derivation on the path that was not.

BOTH ALTERNATIVES WERE PUT AND REJECTED, so neither is re-opened. A SECOND CONDITION, on the anchor and the checked plan resolving to different roots: rejected as two conditions where one does the work, and because it does not reach the typo'd `--source` at all, since a path that does not exist yields no canonical root and a two-root comparison then has nothing to compare. PARSING THE WHOLE `(source, plan, metrics)` TRIPLE at the boundary into one validated checked-target type: rejected ON SCOPE, NOT ON MERIT. It is the cleaner long-term architecture and would make the divergent pairing UNCONSTRUCTIBLE rather than detected, but it touches the resolution `validate`, `status`, `next` and the ledger path all share, it needs its own risk class and probably its own design pass, and it risks re-opening the already-settled `Q-55-refusalscope` split. If it is ever wanted it belongs in the validation-constraints step beside the queued project-identity work, not here.

WHICH PLAN EACH SURFACE READS IS ALREADY DECIDED IN THE TREE, so the rule names an existing branch rather than adding one. `run_validate`'s `--workflow` match reads the TOML source in its `(Some(source), _, Some(metrics_text))` arm and the Markdown `--plan` in its `(None, Some(plan_text), Some(metrics_text))` arm; `run_status` and `run_next` each project from `toml_source(&args.source)` when that yields a TOML-primary source and fall back to `--plan` otherwise (`src/main.rs:run_status`, `src/main.rs:run_next`), which is the same selection in a different spelling. `status --resume` reads NO plan (`src/main.rs:run_resume` derives `<task>` from the source-or-plan filename and reads only the ledger), so it has no checked plan to root on.

THE LEXICAL/CANONICAL SPLIT IS DELIBERATE AND MUST NOT BE COLLAPSED. The DEFAULT is lexical so the derived path keeps the spelling the caller typed; the GUARD is canonical so it cannot be spoofed by a symlinked source. A built the canonicalising DEFAULT too and measured what it costs: every resolved path becomes absolute even when the user typed a relative source, so two of the three printed lines change on the no-regression case and an absolute machine-specific path lands in output that a pre-commit hook or CI log may be matched against. That is why the fork was resolved this way and not the other; the cost of the split is accepted cost (ii) below.

## One predicate, two responses: the validator refuses, the projections omit (`Q-55-refusalscope`)

`Q-55-mechanism`'s text ("a refusal for unsafe pairings, covering `validate`, `next`, `status` and the ledger path") admitted two readings: the refusal on the validator only, or the refusal on all four surfaces. The second planner pass raised the ambiguity rather than deciding it, and the human decided it with a THIRD option that neither reading contained (receipt `q_id:"Q-55-refusalscope"`, options "Omit the unsafe part, exit 0" / "Narrow: refusal on validate only" / "Wide: refusal on all three", chosen OMIT THE UNSAFE PART, EXIT 0).

THE DECISION. `status` and `next` anchor exactly as the validator does. When the pairing is nonetheless UNSAFE, they OMIT THE WORKFLOW-DERIVED FIELDS, say WHY in their place, and EXIT 0. They neither refuse nor project. The refusal (exit non-zero) remains the validator's alone.

THE GROUND, and it is why this option needs no authorisation against Safe on existing projects while the wide reading would have. `README.md:238` does not merely promise the projections never fail; it says "Unlike `validate` it never fails on a missing or malformed file (a missing part is simply left out of the projection)", and `run_resume`'s doc comment (`src/main.rs`) matches it. A LOG THAT DOES NOT BELONG TO THIS PLAN IS EXACTLY A PART THAT IS NOT AVAILABLE FOR THIS PROJECTION. Omitting it is the documented contract applied LITERALLY, not an exception carved into it. The pass's objection to the wide reading (a hard refusal would break a documented never-fails contract) is therefore resolved rather than overridden, and the projections keep both halves of their contract: they still never fail, and they still leave out what they do not have.

A CORRECTION THE SECOND PASS OWES ON ITS OWN TEXT, because it is what makes this decision necessary rather than decorative. That pass wrote that the anchoring "is what actually removes the fabricated `next` instruction and the leaked resume block". THAT IS TRUE ONLY OF THE DEFAULT `--metrics` CASE. Anchoring changes where the DEFAULT resolves; it does nothing to an EXPLICIT `--metrics` naming a foreign log (explorer A's second false pass, explorer C's attack 4, found independently on different models). Without this decision, `next --source <foreign plan> --metrics <this repository's log>` would keep emitting `state: converged` and `next: mark the step complete` after the whole path fix had landed.

### The exact behaviour, per surface

The trigger is the SAME containment predicate the validator's refusal uses. The predicate is never re-implemented per surface (One source of truth).

- `status --resume`. Print a note naming the ledger path that was rejected and why, and print NO part of the block. EXIT 0. THIS SURFACE READS NO PLAN, so the rule SUPPLIES a root rather than being re-implemented per surface (`Q-55-resumepairing`, human, 2026-08-02): a `--source` and a `--plan` that both exist must resolve to the SAME root or the block is omitted, and with one alone the anchor is the root, as today. - `next`. The metrics line is omitted as for `status`, AND the whole `ACTIVE LOOP` block is omitted, AND the `RESUME STATE` echo is omitted when the ledger is the unsafe artifact, with the same note naming the rejected ledger path in its place that `status --resume` prints. In place of the loop, print the existing "no active review loop (`<reason>`)" line with a reason naming the unsafe pairing. `next` MUST NOT EMIT AN ACTION OR A `summary` LINE DERIVED FROM A LOG IT CANNOT VOUCH FOR. This is the specific output the fix must make unreachable, measured by the orchestrator at commit `3170e3f`: `state: converged`, `streak: 1/1`, `rounds: 2/5`, `next: mark the step complete, re-render, and commit`, plus the `summary` line, at exit 0, for a project with ZERO rounds of its own. NOT every field of `ActiveLoop` is round-derived, and this argument does not need them to be: `round_cap` comes from the workflow spec, `isolation_tier` is echoed from the CLI, and the `review_findings`/`triage_findings` slots in `context` are built from the task name, as the last bullet of "Scope: what this step does not do" records.

A TRAP THE IMPLEMENTER MUST AVOID, and the reason this is a design constraint rather than a wording preference. The cheap implementation is to treat an unsafe log as an ABSENT one and let the existing code path run. That is wrong and it fabricates in the other direction: `run_next` (`src/main.rs`, the `else` arm of its `metrics_path.exists()` branch) turns an absent log into an EMPTY rounds list and still projects, so a step at `in-progress` with zero visible rounds yields `state: awaiting-first-review` and `next: spawn a reviewer for the first review round`. For a project whose real log says the step converged, that is a fresh false instruction, quieter than "mark the step complete" but still an instruction derived from evidence the tool does not have. UNSAFE IS NOT ABSENT: absent means "this project has no rounds", unsafe means "this tool cannot tell you anything about this project's rounds", and only the second is what the omission must express.

THE PROJECTION SHAPE ALREADY ADMITS THIS, so no new output structure is needed for the human renderer. `NextProjection` (`src/next.rs`) ALREADY CARRIED `metrics: Option<MetricsSummary>`, `active_loop: Option<ActiveLoop>`, `resume_state: Option<String>` and `no_active_loop_reason: Option<String>`, and `render_human` (`src/next.rs`) ALREADY RENDERED the `None` arms. `status`'s `Projection` carries `metrics: Option<MetricsProjection>` the same way. What the change adds is a new REASON reaching those arms, not a new shape, which is the cheaper and safer half of the work (Make illegal states unrepresentable: the state is already representable).

### The field shape and the value vocabulary

Specified here rather than left to the implementer, because the entire point is that a consumer can TELL THE CAUSES APART, and an under-specified vocabulary would reproduce the defect in a new place. Closed enums, not free strings (Make illegal states unrepresentable), serialised kebab-case, following the in-file precedent of `LoopState` (`src/next.rs`, `#[derive(..., Serialize)]` plus `#[serde(rename_all = "kebab-case")]`, which is what puts `awaiting-reviewers` on the wire in the golden today). THE ENUM IS THE MACHINE VALUE ONLY: the paths a human message names are not carried on it, so the CALLER assembles that message from the paths it already holds, which is what lets a unit variant serialise as a bare token while the human text still names the log and the root.

`metrics_absent_reason`, on BOTH `NextProjection` and `status`'s `Projection`, beside the existing `metrics` field. `Some` exactly when `metrics` is `None`. This reason and `resume_state_absent_reason` below are computed by the CALLER and passed through `NextInputs` alongside `metrics_records` and `resume_state`, so `project` stays a pure function of its inputs.

- `log-absent`: no file found at the resolved metrics path.
- `log-not-this-project`: the resolved path is not under the root, so the tool cannot vouch that its records belong to that plan. This is the `Q-55-refusalscope` case.

`no_active_loop_reason`, on `NextProjection`, RETYPED from `Option<String>` to a closed enum and NO LONGER `#[serde(skip)]`. Retyping is preferred over adding a parallel serialised field: one reason, one type, rendered two ways, rather than two representations of the same fact that can disagree (One source of truth). The human renderer maps each existing variant back to the exact string it prints today, so `render_human` output and its golden are unchanged and the retype is behaviour-preserving on the human surface. `no_loop_reason`'s third string, "no in-progress or ready step", WAS UNREACHABLE for the reason given above and the reconciliation collapsed it to two answers, so no variant is specified for it.

- `no-plan-steps`, printed as today's "no plan steps found".
- `all-steps-terminal`, printed as today's "all steps complete".
- `metrics-not-this-project`, the NEW case: the round log resolved for this plan is not the plan's own, so no loop state can be derived from it. Printed with a reason naming the resolved log and the derived root.

`resume_state_absent_reason`, on `NextProjection`, beside `resume_state`. `Some` exactly when `resume_state` is `None`. This one is included rather than skipped because without it the same defect lands on a third field: after inc2, `next --json` can omit the resume block for a THIRD reason and report the same bare `null` it reports for the other two. Two of the three causes WERE already distinguished IN THE CODE at `src/main.rs:run_next`, where `ledger_path.exists()` being false and `extract_resume_state` returning `None` WERE separate branches that both COLLAPSED to `None`, so naming them COST nothing beyond the naming.

- `ledger-absent`: no file found at the resolved ledger path.
- `no-resume-section`: the ledger exists but carries no `## RESUME STATE` block.
- `ledger-not-this-project`: the resolved ledger is not under the root, which is either an explicit `--ledger-fragment` outside it or, on `next`, a DEFAULT ledger anchored on a `--source` that itself lies outside it. Both members are CONTAINMENT and neither is a project-identity test: a `--source` in a different project reaches this only when that project is not NESTED inside the root.

THE PRECEDENCE RULE, on both path fields: where an absent cause and an unsafe cause both apply, THE UNSAFE VARIANT WINS, because unsafe is not absent (above) and a bare absence is exactly the conflation this vocabulary exists to prevent.

THE CORRELATION RULE, so a consumer can join the fields rather than guess. On an unsafe metrics pairing, `metrics_absent_reason` is `log-not-this-project`, and `no_active_loop_reason` is `metrics-not-this-project` WHEN the loop's absence is metrics-derived rather than step-derived. The shared `not-this-project` token is deliberate: it is the same cause reported as two consequences, and a consumer that recognises the token needs no lookup table to correlate them.

WHAT HAS NO JSON SURFACE AT ALL, so nothing is owed there and no acceptance check demands it: `status --resume` returns from `run_resume` at `src/main.rs:run_status`'s `return run_resume(&args)` early return, BEFORE any serialisation, so `--resume` is human text only and `--json` alongside it is silently ignored today. The implementer must not invent a JSON reason for that path. That the flag is silently ignored is a pre-existing oddity of a shape this project elsewhere constrains in clap (`--ledger-fragment` carries a `requires` for exactly this stated reason at `src/main.rs:StatusArgs::ledger_fragment`, and `audit --out` carries a `conflicts_with = "json"` at `src/main.rs:AuditArgs::out` for the mutually-exclusive-output-modes case this one actually is); it is NOT caused by this step, it was raised rather than folded in, and it is now scheduled as its own backlog step, `status-resume-ignores-json` (order 96).

WHAT WAS CONSIDERED AND DELIBERATELY NOT ADDED. A reason beside `status`'s `plan: Option<PlanProjection>`: that field has exactly ONE cause (no readable plan source was given), so a reason field there would carry a single value and inform nobody (Minimal by default). A malformed-log variant on `metrics_absent_reason`: neither `status` nor `next` distinguishes a malformed log today (`count_records` counts non-blank lines and `parse_rounds` is best-effort), so there is no such state to report, and manufacturing one would be new behaviour rather than a reason for existing behaviour.

## The increments, and why in this order

`Q-55-scope` (human, 2026-07-31, receipt `q_id:"Q-55-scope"`) decided ONE STEP with SEPARATE INCREMENTS, over a separate step ahead of `Q-55` and over folding this into the validation-constraints step, on the reasoning that the defects touch the same code path and produce the same user-facing green, so separate steps would mean reviewing the same region twice while separate increments keep each change reviewable on its own terms. That decision named TWO increments, because the step was then TWO defects. The count is now UNDER-SPECIFIED rather than wrong: what the human decided is the DIVISION PRINCIPLE, and the set below is that principle re-applied to the widened scope, not an appendix to the old pair.

The division follows one rule: an increment is a unit whose review asks ONE question. Where two pieces of work would be reviewed by asking the same question, they are one increment; where they would be reviewed by asking different questions, they are separate.

- `workflow-enforcement-tier-inc1`, THE RESOLUTION RULE AND ALL OF ITS CALL SITES. `--metrics` becomes `Option<PathBuf>` on `ValidateArgs`, `StatusArgs` and `NextArgs`; the lexical nearest-wins derivation and the metrics resolution land; `validate`, `status` and `next` all use them; `default_ledger_path` takes the plan source and resolves the ledger BESIDE it, with both call sites (`run_resume` and `run_next`) passing it through. Plus the help strings and doc comments that describe resolution, and the red-then-green tests. NO new REFUSAL mechanism: any new non-zero exit comes from the pre-existing W3 check finally running against the right project, which is check 4's whole point. With BOTH a `--source` and a `--plan`, the anchor follows the source-then-plan order `derive_task` already uses (`src/next.rs`); with NEITHER, the ledger keeps today's `docs/plans/<task>.ledger.md`, as the metrics rule keeps its CWD-relative path for the same case. The review question is "does the derivation name the right file, in every layout".
- `workflow-enforcement-tier-inc2`, THE CONTAINMENT PREDICATE AND ITS CONSUMERS. The canonical root derivation FROM THE PLAN EACH SURFACE READS (`Q-55-endproperty`, which is what makes the predicate reach a divergent `--source`/`--plan` pairing), the resolve-as-far-as-possible resolution, the predicate itself, and then the responses `Q-55-refusalscope` settled: `validate --workflow` REFUSES (a problem, exit non-zero), `status` and `next` OMIT the affected parts with a reason at exit 0, and `status --resume` omits the block. Plus the serialised reasons `Q-55-jsonreason` settled, so the omission explains itself on `--json` as well as in the human text, with the four falsified doc comments corrected in the same change. Plus the `--workflow` help enumeration, the README notes for the new error, the new omitted part and the new JSON fields, the CHANGELOG entry, and its own red-then-green tests. The review question is "does the predicate identify an unsafe pairing correctly, and does each consumer give the right answer to it, on both surfaces".
- `workflow-enforcement-tier-inc3`, THE TIER POLICY AND THE `SE-3` DOCUMENTATION HALF. The `_` catch-all of `src/main.rs:run_validate`'s `--workflow` match becomes a reported problem so `--workflow` exits non-zero, plain `validate` untouched; the `run_validate` doc comment corrected; `pack/AGENTS.md:93` qualified and the two deployed copies regenerated; the README `validate` paragraph and the CHANGELOG entry. Plus its own red-then-green test. The review question is "is the two-tier boundary now both enforced and truthfully described".
- `workflow-enforcement-tier-inc4`, THE DOCUMENTATION-CURRENCY PASS THAT CLOSES THE STEP, and the only increment here that ships no behaviour. This file's own descriptions of `src/main.rs`, `src/next.rs`, the test suite, `README.md` and `pack/AGENTS.md`, which the three increments above falsified as they landed, re-tensed to the pre-increment state they were written about or deleted where the sentence carried nothing else; the acceptance-check preamble's stale count of the red-then-green demonstrations inc2 owes, deleted rather than corrected; acceptance check 16, widened to pin the probe that cannot answer beside the log that is absent; the citation drift this step's own line-number movement caused in the sidecars of `test-tmpdir-repo-assumption` (order 95), `checks-runner-worktree-name-collision` (order 93) and `instrument-magic-filename` (order 60); `Projection.plan`'s false doc comment at `src/main.rs:Projection` (`Q-55-plandoccurrency`); and this description. The review question is "does every claim this step leaves behind match the tree it leaves behind".

WHY THE FOUR CALL SITES ARE ONE INCREMENT AND NOT TWO OR THREE. They share one function. Splitting `validate`'s anchoring from the siblings' would review the same derivation twice, which is exactly what `Q-55-scope` rejected at the step level, and it would leave the tree in a state where two commands disagree about which log belongs to a plan, an inconsistency neither endpoint has and one that an implementer and a reviewer would each have to reason about. The ledger's finding that the projections are "arguably the MORE urgent half" points the same way: deferring them to a later increment is the wrong direction. The ledger path is a genuinely DIFFERENT rule (the source's own directory, no upward walk, no fallback) and a different defect class (content injection rather than a wrong count), but it is roughly ten lines; giving ten lines their own convergence loop is disproportionate (Minimal by default). It stays in inc1, and this paragraph exists so a reviewer does not expect the upward walk there and flag its absence.

WHY THE PREDICATE IS ITS OWN INCREMENT. It carries a known false positive (accepted cost (ii)); and it deliberately uses a DIFFERENT resolution from the default, so its review must check the lexical/canonical SPLIT rather than one rule. Its correctness property is also a negative ("must never pair..."), which the design pass showed is not established by passing the obvious tests: the anchor passed the first pass's own reproduction while leaving two further false passes standing.

WHY THE OMIT BEHAVIOUR LANDS IN INC2 AND NOT IN INC1, WHICH IS NOT WHERE IT FIRST LOOKS LIKE IT BELONGS. It is the projections' own behaviour, not the containment refusal, so inc1 is the natural first guess. The derivation forces inc2, for two reasons. FIRST, the omit is TRIGGERED BY THE CONTAINMENT PREDICATE and by nothing cheaper: no lexical test separates an explicit `--metrics` naming a foreign log from an explicit `--metrics` naming the plan's own log spelled differently; A's guard exists because the lexical comparison gets the symlink case wrong. Putting the omit in inc1 therefore means putting the PREDICATE in inc1, which drags inc2's hardest review question (a negative property, established only by adversarial construction) forward into an increment whose question is a positive one, and leaves inc2 as a bool turned into a `problems.push`. SECOND, the responses are only reviewable AGAINST EACH OTHER. The whole content of `Q-55-refusalscope` is that one predicate yields DIFFERENT answers on the validator and on the projections, so the defect to catch is a consumer wired to the wrong response, which is invisible unless they are read side by side. The same applies to accepted cost (ii): the symlinked-`docs/plans` false positive now has TWO manifestations, a loud false refusal in `validate` and a QUIET FALSE OMISSION in `status` and `next`, and those are not equally acceptable (a false omission in a surface an agent consumes withholds true evidence without saying anything is wrong with the tool), so the judgement has to be made over both at once or it is not made at all.

WHY THE SERIALISED REASONS LAND IN INC2 TOO, derived rather than assumed. The tempting framing is that this is the same predicate yielding a THIRD response, which would put it in inc2 by the argument above. That framing is wrong and the right one is stronger: the JSON reason is not a third response, it is the SECOND RENDERING of one response. The predicate yields two responses (refuse, omit), and the omit has two renderings (human text, JSON). Splitting the renderings across increments would mean inc2 COMPUTES a reason, prints it to text, and discards it for JSON, and a later increment re-surfaces a value that already existed, which is a deliberate half-done state across a boundary bought for nothing. Worse, it would ship a NEW behaviour with its explanation missing on exactly the surface the behaviour exists for: `Q-55-refusalscope` is about output an agent acts on, and an agent reads `--json`. That is a different and weaker position than the inc1-to-inc2 gap, which leaves an EXISTING defect open for one increment rather than shipping a new silence. Two mechanical reasons agree: the enums are consumed by the same code that computes the omission, and `status --json` has no golden test, so separating the JSON work would land the unguarded half of it with no co-located human-renderer behaviour to check it against and would force the acceptance check to rebuild the unsafe fixture a second time. One fixture answers both surfaces if they land together.

THE COST OF THAT PLACEMENT, STATED RATHER THAN HIDDEN. After inc1 alone, `next --source <foreign plan> --metrics <this repository's log>` STILL emits `state: converged` and `next: mark the step complete`. That is a known defect deliberately left open across an increment boundary, exactly as inc1 alone leaves defect A open by design, and it is the reason inc2 is not optional polish: inc2 closes the agent-facing half of defect C, which the design pass judged the more urgent half. An implementer must not read inc1's acceptance checks as evidence that defect C is closed.

WHY THE DOCUMENTATION HALF SHIPS WITH THE TIER POLICY AND NOT SEPARATELY. The pack sentence's truth is a FUNCTION of the tier policy's behaviour, so reviewing the sentence requires running the tier policy's cases; separating them would make the second reviewer redo the first reviewer's runs. More importantly, the interval between them is not neutral: as set out under defect D, a tier policy without its qualifier leaves a non-instrumented user hitting a hard error from a check the guidance still promises them unconditionally, which is worse than the gap either change leaves alone. The mechanism documentation for inc1 and inc2 (help strings, the README anchoring note, the doc comments) travels with ITS increment for the same currency reason, and there is deliberately NO separate documentation increment for the SHIPPED prose: this project already carries a step about documentation currency, and shipping behaviour with stale prose beside it is the defect that step exists to remove. THIS FILE'S OWN CLAIMS ABOUT THE TREE ARE THE ONE EXCEPTION, and they are inc4; the Documentation impact section states why that exception is measured rather than preferred.

THE ORDER IS inc1 -> inc2 -> inc3 -> inc4, AND EVERY EDGE IS LOAD-BEARING. INC4'S EDGE IS THE CHEAPEST TO STATE AND WAS MEASURED RATHER THAN ARGUED: inc1's own review converted a set of `src/main.rs` citations, and inc2 and inc3 falsified them again, so a currency pass that runs while the code is still moving is provably wasted work. It runs when the code stops moving, which is after inc3 and before the step goes `complete`. The first planner pass argued that the path fix must precede the tier policy, because a user whose `--workflow` run started failing could "fix" it by running from a directory that happens to contain a log, which is exactly the contaminated green of defect B, so the tier policy would hand users a workaround into the worse bug. THAT ARGUMENT STILL BINDS, and the design pass GENERALISES it: the tier policy goes LAST because EVERY escape hatch a user reaches for is closed by an earlier increment. Standing somewhere else is closed by inc1. Passing `--metrics` by hand at a foreign log is closed by inc2, and it is not hypothetical: it is explorer A's second false pass and explorer C's attack 4, found independently on different models. Landing the tier policy before either would convert a quiet defect into a loud prompt to reach for the two workarounds that are still open. Inc1 precedes inc2 because the guard reuses inc1's root derivation, and because a guard without an anchor is candidate (b) standing alone, which refuses every cross-directory run until the user passes `--metrics` by hand, the objection the first pass correctly raised against (b) as an alternative.

## Risk classification

Each increment is argued on its own evidence. The first pass's "both risky" is NOT inherited; of the three arguments that pass could have reached, two are new here and the third has gained a factor it did not have.

`workflow-enforcement-tier-inc1` is RISKY (two consecutive clean rounds). It changes WHICH FILE the tool reads on every invocation of THREE commands that do not pass `--metrics`, plus which LEDGER two of them read, and the failure mode of a wrong anchor is not a crash but a confident wrong answer. The design pass measured that this failure mode IS SELF-CONCEALING: A's own build, correct on the reported reproduction, was still emitting `workflow invariants hold` at exit 0 on two other inputs until A attacked it deliberately, and nothing in the output distinguished the correct runs from the wrong ones. That is the same class of defect the increment exists to remove. It also COMPOUNDS FORWARD: after inc3 a mis-derived anchor stops being "reads the wrong file" and becomes "hard-fails a correctly instrumented project", so an inc1 defect escalates into a broken gate rather than staying a quiet one. The derivation additionally makes at least one SILENT JUDGEMENT CALL that no measurement settled (nearest-wins on a nested `docs/plans`), which is precisely the kind of thing a review round exists to catch. Relative-path handling is this tree's recorded weak spot rather than a neutral area: `is_safe_sidecar_ref` (`src/plan/source.rs:480-495`) exists because of it, and two backlog steps sit in the same family (`sidecar-ref-empty-string` order 63, `sidecar-ref-symlink` order 64). The counter-argument, that the eventual diff is small (A measured the anchor at `+79/-15`, mostly comments) and that there is a deterministic test for it, loses to the blast radius: every future invocation of the project's main validation surface, plus the agent-facing `next`, whose wrong answer is an instruction rather than a report.

`workflow-enforcement-tier-inc2` is RISKY (two consecutive clean rounds), and for reasons that do not overlap inc1's. It INTRODUCES a non-zero exit on validator invocations that succeeded before inc2 AND withholds output from projection invocations that answered before inc2, and it does so with a MEASURED FALSE POSITIVE already in hand (accepted cost (ii), the symlinked `docs/plans` directory), so it is a deliberate, knowing break of Safe on existing projects rather than a strict tightening. Its correctness property is a NEGATIVE, and the design pass demonstrated that a build satisfying the stated reproduction can still admit the defect class by two other routes, so passing the increment's own tests is explicitly NOT sufficient evidence here; the review has to include adversarial construction, which is what a second clean round buys. It is also the only place in the mechanism where TWO DIFFERENT RESOLUTIONS (lexical default, canonical guard) run against each other by design, and the disagreement between them is simultaneously the source of the guard's strength (it cannot be spoofed by a symlinked source) and of its one false positive, so a reviewer who checks only one of the two has not checked the mechanism. `Q-55-endproperty` SHARPENS THAT RATHER THAN ADDING A CLASS: the two resolutions can now start from DIFFERENT FILES, the log from the `--source`-first anchor and the root from the plan the check reads, so rooting the guard on the anchor is a defect that check 11 passes over. `Q-55-refusalscope` ADDS A FACTOR RATHER THAN LEAVING THE CLASS UNCHANGED: one predicate now drives responses, two of which must NOT fail, so the failure this increment can ship is not only "refuses the wrong thing" but "refuses on a surface that must never refuse" or "omits on a surface that should have refused", and its false positive is now partly SILENT, since a false omission in `next` withholds true evidence from an agent without signalling that anything went wrong. `Q-55-jsonreason` adds a second: the increment now also changes a DOCUMENTED JSON CONTRACT on two commands, falsifying four doc comments and breaking a byte-compare golden. None of this changes the class, since the increment was already `risky`, but it widens what the two rounds have to cover and a reviewer who checks only `next --json` has checked the guarded half. The counter-argument, that it is roughly 80 lines sharing inc1's derivation, is about diff size and not about blast radius, which this project has already recorded losing.

`workflow-enforcement-tier-inc3` is RISKY (two consecutive clean rounds). It changes a CLI EXIT CODE, the most externally depended-on contract the tool has, and it is INTENDED to flip a currently-passing gate to failing for every non-instrumented project, which is exactly the population Safe on existing projects protects. That principle is not overridden lightly; what authorises the break is Structured data first, project for humans, whose own text records the human's 2026-07-18 decision that at this pre-adoption stage the best long-term design wins over backwards-compatibility and that it beats Safe on existing projects where the two conflict. AN AUTHORISED BREAK IS A REASON TO MAKE THE CHANGE, NOT A REASON TO REVIEW IT LESS. The boundary is easy to get subtly wrong in a way tests may not catch by accident: the `_` catch-all of `src/main.rs:run_validate`'s `--workflow` match covers BOTH the TOML-source-present and the Markdown-plan-present variants of "metrics missing", and the fix must convert exactly those to problems without capturing a case that should stay a skip and without touching the no-`--workflow` path at all. THE FACTOR THE FIRST PASS DID NOT HAVE: this increment now also edits the SHIPPED PACK and regenerates two DRIFT-GUARDED deployed files, and its pack content is a COVERAGE CLAIM about an enforcement boundary. That is the one artifact species this project has calibration data on, and the data is bad: step 92 spent six rounds and fifteen findings on one such claim, all of them prose, zero mechanism defects, joint-third of the artifacts ever reviewed against a project median of two rounds, with the ledger's own diagnosis being that "a coverage claim is unusually easy to falsify at an edge". The counter-argument, that the in-tree precedent of that match's `(None, None, _)` arm (`src/main.rs:run_validate`) makes the code half a three-line change, is true and does not reach the other half.

`workflow-enforcement-tier-inc4` is RISKY (two consecutive clean rounds), classified at loop-open so the required count is a PROPERTY OF THE ARTIFACT rather than a fresh judgement each round, which is what the convergence rule demands. The artifact is a DOCUMENTATION-CLAIM SURFACE, and that is this project's measured worst review class on its own calibration data. Step 92 (`prompt-drift-guard`) spent SIX rounds and FIFTEEN valid findings on ONE coverage claim, all of them prose and none of them a mechanism defect. Inc1 OF THIS VERY STEP spent THREE rounds and 13 valid findings, EVERY ONE an inaccurate description of correct behaviour and zero defects in what the code does. The counter-argument, that a documentation pass changes no behaviour so one clean round is enough, is the precise reasoning that produced both of those loops, so it is recorded here as REJECTED rather than left for a reviewer to re-derive. Two factors are specific to this increment and neither is present in inc1 to inc3. FIRST, ITS FAILURE MODE IS THE ONE IT EXISTS TO REMOVE: a pass that re-tenses a false claim can write a NEW false claim in its place, and this project has five retrospective and one prospective measurement that a fix pass which AUTHORS prose manufactures the next round's finding while a deletion-class pass re-seeds nothing, so a reviewer must check what was written and not only what was removed. SECOND, ITS EVIDENCE IS MECHANICAL AND CHEAP TO PRODUCE, which cuts the other way: every claim here is a citation or a quotation, so a round that reads prose without opening the cited range has not reviewed it, and the acceptance check below is stated so that the round report can show the ranges rather than assert the conclusion.
