## Defect A, the false green (`Q-55` proper)

CORRECTION TO `Q-55`'S OWN WORDING, which the implementer should not carry forward. `Q-55` says `validate --workflow` "silently passes". That is an OVERSTATEMENT: the skip IS announced, twice, at `src/main.rs:845` and `src/main.rs:1001-1003`. The correction is sharper than it first looks, because both announcements go to STDERR (both are `eprintln!`), while the only thing on stdout is the ok summary. The operative defect is therefore the EXIT CODE and nothing else: a CI gate reads the exit status, not the stderr log, so `validate --workflow` returns success for a project with zero machine enforcement of any workflow invariant. Write it up as a false green, never as a silent one. Explorer B captured the streams separately at the pre-change build and confirmed stderr empty on the defect-B invocation and non-empty here, which is what makes the distinction measured rather than asserted.

THE MECHANISM. The `--workflow` block is a four-arm `match` at `src/main.rs:958-1004` over `(toml_primary, &plan_contents, &metrics_contents)`. The arm that fires here is the `_` catch-all at `src/main.rs:999-1003`, which prints the skip note and pushes NO problem, so `problems` stays empty and `run_validate` takes the success branch at `src/main.rs:1007-1011`.

THE DECIDED REMEDY (human, 2026-07-31, receipt `q_id:"Q-55"`): FAIL WHEN `--workflow` CANNOT RUN. When `--workflow` is explicitly requested and no metrics log exists at the resolved path, the run exits non-zero and reports why. Plain `validate` (and `validate --source` / `--plan` without `--workflow`) is UNAFFECTED: an absent log there stays a stderr note and exit 0, because nobody asked for the check. The reasoning the human accepted: the user explicitly asked for the workflow check, so skipping it and reporting success is the defect. The policy applies to the resolved metrics path however it was resolved, whether from the anchored default or from an explicit `--metrics` value; "the user named a path that does not exist" is not a weaker case than "the default path does not exist".

WHAT WAS REJECTED, AND WHY. Make round-logging CORE rather than opt-in: rejected as forcing instrumentation on users who did not ask for it, and a substantially bigger change than the defect warrants (Minimal by default; the `--instrument` opt-in is the two-tier design working as intended, not the bug). Warn but keep exit 0: rejected because a warning with exit 0 is still green in CI, which is the actual failure mode being fixed; it would leave the defect in place and add a message beside it.

THE PRECEDENT THIS FOLLOWS, ALREADY IN THE TREE, so this is closing the second half of a hole whose first half is already closed. The sibling arm at `src/main.rs:992-998` handles "`--workflow` requested but no plan source resolved" and pushes a hard problem, with the comment stating the identical reasoning: "`--workflow` was explicitly requested, so skipping would green-pass while checking nothing; make it a hard problem instead." That test's own comment at `:96-98` records the gap this step closes: "with a source present but metrics missing the tool still soft-skips". Defect A is the same defect on the other input, and the fix is the same shape.

A CASE THAT IS NOT PART OF THIS, named so the work does not creep into it. That is simpler than the metrics rule and has fewer cases that can go wrong: no upward walk, no fallback branch, no convention to miss.

## The mechanism, decided rather than chosen here

`Q-55-mechanism` (human, 2026-07-31, receipt `q_id:"Q-55-mechanism"`): ANCHOR PLUS REFUSAL, IDENTITY QUEUED. Ship candidate (a), the metrics path anchored to the plan source, PLUS a refusal for unsafe pairings, covering `validate`, `next`, `status` and the ledger path, and QUEUE project identity in the round record to the validation-constraints step. The human declined both the wider option (identity fields in the same step) and the narrower one (anchor only). The recorded reasoning: the pass measured that anchoring alone leaves the DEFECT CLASS open, so the refusal is not gold-plating, while pulling identity in would edit the record schema that W3, W4 and W5 all read, which the calibration close already argued should be ONE deliberate edit rather than a rider on a path fix.

The implementer does NOT re-open any of the following. Each is recorded with the measurement that settled it.

DISTINGUISHING A DEFAULTED `--metrics` FROM AN EXPLICIT ONE: use `Option<PathBuf>` with a bare `#[arg(long)]`, and apply the default after resolution. Do NOT use clap's `ArgMatches::value_source`. The reason is NOT the 17 lines saved. Explorer A built both routes to a working state and then FORCED the `value_source` failure mode by renaming the argument id, simulating a later field rename. Both the subcommand and the argument are addressed by STRING, so in a DEBUG build clap panics (`` `"metrics_typo"` is not an id of an argument or a group ``, exit 101) while in a RELEASE build the same code silently answers "not supplied", so the user's explicit `--metrics docs/metrics/workflow.jsonl` is IGNORED and a different file is read with no message. That is a debug/release behaviour divergence, guarded only by clap's `debug_assertions`, in the code path whose entire purpose is deciding which file to read: the same self-concealing class as the defect under repair, which is what makes it disqualifying rather than merely uglier. Two lesser measured costs: `value_source` is `+96/-13` against `Option<PathBuf>`'s `+79/-15` for identical behaviour, and clap prints the `default_value` it was given with no way to keep the value and suppress the display, so `--help` would carry a now-false `[default: docs/metrics/workflow.jsonl]`. This independently vindicates Make illegal states unrepresentable, which A was told to TEST rather than repeat.

THE DERIVATION: a purely LEXICAL, NEAREST-WINS upward search. Start at the source's parent directory and walk up; the first ancestor whose own file name is `plans` and whose parent's file name is `docs` identifies `<root>/docs/plans`, and the root is that ancestor's grandparent. No filesystem access and no canonicalisation. The metrics default is then `<root>/docs/metrics/workflow.jsonl`. With neither a `--source` nor a `--plan` there is nothing to anchor to, so the historical CWD-relative path stands unchanged.

THE CONVENTIONLESS CASE, decided by `Q-55-noconvention` (receipt `q_id:"Q-55-noconvention"`): when no `docs/plans`-shaped ancestor exists, FALL BACK TO THE SOURCE'S OWN DIRECTORY, with the containment refusal layered on top. Chosen over a hard error. A had MEASURED the fallback resolving the `--source myplan.plan.toml`-at-a-repository-root case correctly, both from that root and from elsewhere, and Safe on existing projects favours resolving a legitimate layout over rejecting it. This is the case the first planner pass called "no convention to lean on"; there is one, and it is the same answer the CWD-relative default would have given from the right directory.

WHAT THE DERIVATION WAS MEASURED AGAINST. A built a case matrix in which every candidate log location carries a DIFFERENT record count, so the printed count identifies which file was actually read, then ran it. The `docs/plans` convention resolves correctly in every spelling constructed: absolute, relative, `./`-prefixed, and with a `..` inside the path (that last works because `Path::file_name` returns `None` for a `..` component, so the walk skips past it and still finds the real `docs/plans` above). A plan at a root with no `docs/plans` resolves through the fallback. A subdirectory under `docs/plans` resolves to the project root. The rule never consults `.git`, so a nested repository and a directory outside any repository behave identically and correctly; "project root" here is a FILENAME CONVENTION, not a VCS fact, which is a feature (no VCS dependency, works in a tarball) and should be written up as one. ONE CASE IS A JUDGEMENT CALL AND IS RECORDED AS SUCH: a second `docs/plans` in the parent chain resolves NEAREST-WINS to the inner project. A chose it on the reasoning that the innermost project owns the plan, and reported it as "the only place I chose between two defensible answers without external evidence". It is not evidenced; an implementer or reviewer may revisit it on evidence, and must not treat it as settled by measurement.

THE REFUSAL (candidate (b), layered on top). Before the four-arm match in `run_validate`'s `--workflow` block, derive the plan source's root from its REAL (canonicalised) location, resolve the metrics path by absolutising and canonicalising its longest existing ancestor and re-appending the components below it (so a log whose leaf does not exist yet still has its directory prefix resolved), and push a problem when the resolved log is not under that root. A's measured message shape, which reports both paths and the root and tells the user what to do: "`--workflow` would join <source> against <metrics>, which is not under the plan's project root <root>; pass a `--metrics` under that root, or run against the plan's own log". Measured to close both of A's self-found false passes and to resist a `..` escape that climbs out of a fixture root to reach agent-scaffold's own 235-record log.

THE LEXICAL/CANONICAL SPLIT IS DELIBERATE AND MUST NOT BE COLLAPSED. The DEFAULT is lexical so the printed path stays relative and output on the correct case is byte-identical; the GUARD is canonical so it cannot be spoofed by a symlinked source. A built the canonicalising DEFAULT too and measured what it costs: every resolved path becomes absolute even when the user typed a relative source, so two of the three printed lines change on the no-regression case and an absolute machine-specific path lands in output that a pre-commit hook or CI log may be matched against. That is why the fork was resolved this way and not the other; the cost of the split is accepted cost (ii) below.

## One predicate, two responses: the validator refuses, the projections omit (`Q-55-refusalscope`)

`Q-55-mechanism`'s text ("a refusal for unsafe pairings, covering `validate`, `next`, `status` and the ledger path") admitted two readings: the refusal on the validator only, or the refusal on all four surfaces. The second planner pass raised the ambiguity rather than deciding it, and the human decided it with a THIRD option that neither reading contained (receipt `q_id:"Q-55-refusalscope"`, options "Omit the unsafe part, exit 0" / "Narrow: refusal on validate only" / "Wide: refusal on all three", chosen OMIT THE UNSAFE PART, EXIT 0).

THE DECISION. `status` and `next` anchor exactly as the validator does. When the pairing is nonetheless UNSAFE, they OMIT THE WORKFLOW-DERIVED FIELDS, say WHY in their place, and EXIT 0. They neither refuse nor project. The refusal (exit non-zero) remains the validator's alone.

THE GROUND, and it is why this option needs no authorisation against Safe on existing projects while the wide reading would have. `README.md:226` does not merely promise the projections never fail; it says "Unlike `validate` it never fails on a missing or malformed file (a missing part is simply left out of the projection)", and `run_resume`'s doc comment at `src/main.rs:1150-1151` matches it ("A missing ledger or absent section prints a note and exits 0, since `status` is a best-effort projection, not a validator"). A LOG THAT DOES NOT BELONG TO THIS PLAN IS EXACTLY A PART THAT IS NOT AVAILABLE FOR THIS PROJECTION. Omitting it is the documented contract applied LITERALLY, not an exception carved into it. The pass's objection to the wide reading (a hard refusal would break a documented never-fails contract) is therefore resolved rather than overridden, and the projections keep both halves of their contract: they still never fail, and they still leave out what they do not have.

A CORRECTION THE SECOND PASS OWES ON ITS OWN TEXT, because it is what makes this decision necessary rather than decorative. That pass wrote that the anchoring "is what actually removes the fabricated `next` instruction and the leaked resume block". THAT IS TRUE ONLY OF THE DEFAULT `--metrics` CASE. Anchoring changes where the DEFAULT resolves; it does nothing to an EXPLICIT `--metrics` naming a foreign log, and the explicit case is precisely what survives it (explorer A's second false pass, explorer C's attack 4, found independently on different models). Without this decision, `next --source <foreign plan> --metrics <this repository's log>` would keep emitting `state: converged` and `next: mark the step complete` after the whole path fix had landed.

### The exact behaviour, per surface

The trigger in all three cases is the SAME containment predicate the validator's refusal uses (the canonically-derived plan root, and whether the resolved artifact lives under it). One predicate, three consumers, three responses. The predicate is never re-implemented per surface (One source of truth).

- `status`. The metrics half is omitted: print `metrics: unavailable, <reason>` in place of `metrics: <n> records`, where the reason names the resolved log, the derived project root, and that the two do not correspond. The plan half is unaffected and still prints. EXIT 0.
- `status --resume`. Print a note naming the ledger path that was rejected and why, and print NO part of the block. EXIT 0. The DEFAULT ledger case is already closed by the anchoring in inc1 (explorer B measured the post-fix run printing "no ledger at <fixture path>; nothing to resume"); what this rule adds is the residual, an explicit `--ledger-fragment` naming a ledger outside the plan's root.
- `next`. The metrics line is omitted as for `status`, AND the whole `ACTIVE LOOP` block is omitted, AND the `RESUME STATE` echo is omitted when the ledger is the unsafe artifact. In place of the loop, print the existing "no active review loop (`<reason>`)" line with a reason naming the unsafe pairing.

`next` MUST NOT EMIT AN ACTION OR A `summary` LINE DERIVED FROM A LOG IT CANNOT VOUCH FOR. This is the specific output the fix must make unreachable, measured by the orchestrator at commit `3170e3f`: `state: converged`, `streak: 1/1`, `rounds: 2/5`, `next: mark the step complete, re-render, and commit`, plus the `summary` line, at exit 0, for a project with ZERO rounds of its own. Every field of `ActiveLoop` is derived from the rounds, including `role`, `prompt`, `context`, `reminders` and `filled_prompt_summary`, so the block goes as a unit; suppressing only the `next:` line would leave an instruction assembled from foreign evidence in the surrounding fields.

A TRAP THE IMPLEMENTER MUST AVOID, and the reason this is a design constraint rather than a wording preference. The cheap implementation is to treat an unsafe log as an ABSENT one and let the existing code path run. That is wrong and it fabricates in the other direction: `run_next` (`src/main.rs:1200-1205`) turns an absent log into an EMPTY rounds list and still projects, so a step at `in-progress` with zero visible rounds yields `state: awaiting-first-review` and `next: spawn a reviewer for the first review round`. For a project whose real log says the step converged, that is a fresh false instruction, quieter than "mark the step complete" but still an instruction derived from evidence the tool does not have. UNSAFE IS NOT ABSENT: absent means "this project has no rounds", unsafe means "this tool cannot tell you anything about this project's rounds", and only the second is what the omission must express.

THE PROJECTION SHAPE ALREADY ADMITS THIS, so no new output structure is needed for the human renderer. `NextProjection` (`src/next.rs:99-118`) already carries `metrics: Option<MetricsSummary>`, `active_loop: Option<ActiveLoop>`, `resume_state: Option<String>` and `no_active_loop_reason: Option<String>`, and `render_human` (`src/next.rs:1017-1043`) already renders the `None` arms. `status`'s `Projection` carries `metrics: Option<MetricsProjection>` the same way. What the change adds is a new REASON reaching those arms, not a new shape, which is the cheaper and safer half of the work (Make illegal states unrepresentable: the state is already representable).

### The field shape and the value vocabulary

Specified here rather than left to the implementer, because the entire point is that a consumer can TELL THE CAUSES APART, and an under-specified vocabulary would reproduce the defect in a new place. Closed enums, not free strings (Make illegal states unrepresentable), serialised kebab-case, following the in-file precedent of `LoopState` (`src/next.rs:187-189`, `#[derive(..., Serialize)]` plus `#[serde(rename_all = "kebab-case")]`, which is what puts `awaiting-reviewers` on the wire in the golden today). THE ENUM IS THE MACHINE VALUE ONLY: the paths a human message names are not carried on it, so the CALLER assembles that message from the paths it already holds (`run_status` and `run_next`), which is what lets a unit variant serialise as a bare token while the human text still names the log and the root.

`metrics_absent_reason`, on BOTH `NextProjection` and `status`'s `Projection`, beside the existing `metrics` field. `Some` exactly when `metrics` is `None`.

- `log-absent`: no file at the resolved metrics path.
- `log-not-this-project`: the resolved path is not under the plan's project root, so the tool cannot vouch that its records belong to this plan. This is the `Q-55-refusalscope` case.

`no_active_loop_reason`, on `NextProjection`, RETYPED from `Option<String>` to a closed enum and NO LONGER `#[serde(skip)]`. Retyping is preferred over adding a parallel serialised field: one reason, one type, rendered two ways, rather than two representations of the same fact that can disagree (One source of truth). The human renderer maps each existing variant back to the exact string it prints today, so `render_human` output and its golden are unchanged and the retype is behaviour-preserving on the human surface. `no_loop_reason`'s third string, "no in-progress or ready step", is UNREACHABLE for the reason given above and the reconciliation collapses it to two answers, so no variant is specified for it.

- `no-plan-steps`, printed as today's "no plan steps found".
- `all-steps-complete`, printed as today's "all steps complete".
- `metrics-not-this-project`, the NEW case: the round log resolved for this plan is not the plan's own, so no loop state can be derived from it. Printed with a reason naming the resolved log and the derived root.

`resume_state_absent_reason`, on `NextProjection`, beside `resume_state`. `Some` exactly when `resume_state` is `None`. This one is included rather than skipped because without it the same defect lands on a third field: after inc2, `next --json` can omit the resume block for a THIRD reason and report the same bare `null` it reports for the other two. The three causes are already distinguished IN THE CODE at `src/main.rs:1208-1212`, where `ledger_path.exists()` being false and `extract_resume_state` returning `None` are separate branches that both collapse to `None`, so naming them costs nothing beyond the naming.

- `ledger-absent`: no file at the resolved ledger path.
- `no-resume-section`: the ledger exists but carries no `## RESUME STATE` block.
- `ledger-not-this-project`: an explicit `--ledger-fragment` resolves outside the plan's project root.

THE PRECEDENCE RULE, on both path fields: where an absent cause and an unsafe cause both apply, THE UNSAFE VARIANT WINS, because unsafe is not absent (above) and a bare absence is exactly the conflation this vocabulary exists to prevent.

THE CORRELATION RULE, so a consumer can join the fields rather than guess. On an unsafe metrics pairing, `metrics_absent_reason` is `log-not-this-project`, and `no_active_loop_reason` is `metrics-not-this-project` WHEN the loop's absence is metrics-derived rather than step-derived. The shared `not-this-project` token is deliberate: it is the same cause reported as two consequences, and a consumer that recognises the token needs no lookup table to correlate them.

WHAT HAS NO JSON SURFACE AT ALL, so nothing is owed there and no acceptance check demands it: `status --resume` returns from `run_resume` at `src/main.rs:1067-1069` BEFORE any serialisation, so `--resume` is human text only and `--json` alongside it is silently ignored today. The implementer must not invent a JSON reason for that path. That the flag is silently ignored is a pre-existing oddity of a shape this project elsewhere constrains in clap (`--ledger-fragment` carries a `requires` for exactly this stated reason at `src/main.rs:465`, and `audit --out` carries a `conflicts_with = "json"` at `src/main.rs:557` for the mutually-exclusive-output-modes case this one actually is); it is NOT caused by this step, it was raised rather than folded in, and it is now scheduled as its own backlog step, `status-resume-ignores-json` (order 96).

WHAT WAS CONSIDERED AND DELIBERATELY NOT ADDED. A reason beside `status`'s `plan: Option<PlanProjection>`: that field has exactly ONE cause (no readable plan source was given), so a reason field there would carry a single value and inform nobody (Minimal by default). A malformed-log variant on `metrics_absent_reason`: neither `status` nor `next` distinguishes a malformed log today (`count_records` counts non-blank lines and `parse_rounds` is best-effort), so there is no such state to report, and manufacturing one would be new behaviour rather than a reason for existing behaviour.

## The three increments, and why in this order

`Q-55-scope` (human, 2026-07-31, receipt `q_id:"Q-55-scope"`) decided ONE STEP with SEPARATE INCREMENTS, over a separate step ahead of `Q-55` and over folding this into the validation-constraints step, on the reasoning that the defects touch the same code path and produce the same user-facing green, so separate steps would mean reviewing the same region twice while separate increments keep each change reviewable on its own terms. That decision named TWO increments, because the step was then TWO defects. The count is now UNDER-SPECIFIED rather than wrong: what the human decided is the DIVISION PRINCIPLE, and the set below is that principle re-applied to the widened scope, not an appendix to the old pair.

The division follows one rule: an increment is a unit whose review asks ONE question. Where two pieces of work would be reviewed by asking the same question, they are one increment; where they would be reviewed by asking different questions, they are separate.

- `workflow-enforcement-tier-inc1`, THE RESOLUTION RULE AND ALL OF ITS CALL SITES. `--metrics` becomes `Option<PathBuf>` on `ValidateArgs`, `StatusArgs` and `NextArgs`; the lexical nearest-wins derivation and the metrics resolution land; `validate`, `status` and `next` all use them; `default_ledger_path` takes the plan source and resolves the ledger BESIDE it, with both call sites (`run_resume` and `run_next`) passing it through. Plus the help strings and doc comments that describe resolution, and the red-then-green tests. NO new REFUSAL mechanism: any new non-zero exit comes from the pre-existing W3 check finally running against the right project, which is check 4's whole point. With BOTH a `--source` and a `--plan`, the anchor follows the source-then-plan order `derive_task` already uses (`src/next.rs:997-999`); with NEITHER, the ledger keeps today's `docs/plans/<task>.ledger.md`, as the metrics rule keeps its CWD-relative path for the same case. The review question is "does the derivation name the right file, in every layout".
- `workflow-enforcement-tier-inc2`, THE CONTAINMENT PREDICATE AND ITS CONSUMERS. The canonical root derivation, the resolve-as-far-as-possible resolution, the predicate itself, and then the responses `Q-55-refusalscope` settled: `validate --workflow` REFUSES (a problem, exit non-zero), `status` and `next` OMIT the affected parts with a reason at exit 0, and `status --resume` omits the block for an explicit `--ledger-fragment` outside the root. Plus the serialised reasons `Q-55-jsonreason` settled, so the omission explains itself on `--json` as well as in the human text, with the three falsified doc comments corrected in the same change. Plus the `--workflow` help enumeration, the README notes for the new error, the new omitted part and the new JSON fields, the CHANGELOG entry, and its own red-then-green tests. The review question is "does the predicate identify an unsafe pairing correctly, and does each consumer give the right answer to it, on both surfaces".
- `workflow-enforcement-tier-inc3`, THE TIER POLICY AND THE `SE-3` DOCUMENTATION HALF. The `_` catch-all at `src/main.rs:999-1003` becomes a reported problem so `--workflow` exits non-zero, plain `validate` untouched; the `run_validate` doc comment corrected; `pack/AGENTS.md:93` qualified and the two deployed copies regenerated; the README `validate` paragraph and the CHANGELOG entry. Plus its own red-then-green test. The review question is "is the two-tier boundary now both enforced and truthfully described".

WHY THE FOUR CALL SITES ARE ONE INCREMENT AND NOT TWO OR THREE. They share one function. Splitting `validate`'s anchoring from the siblings' would review the same derivation twice, which is exactly what `Q-55-scope` rejected at the step level, and it would leave the tree in a state where two commands disagree about which log belongs to a plan, an inconsistency neither endpoint has and one that an implementer and a reviewer would each have to reason about. The ledger's finding that the projections are "arguably the MORE urgent half" points the same way: deferring them to a later increment is the wrong direction. The ledger path is a genuinely DIFFERENT rule (the source's own directory, no upward walk, no fallback) and a different defect class (content injection rather than a wrong count), but it is roughly ten lines; giving ten lines their own convergence loop is disproportionate (Minimal by default). It stays in inc1, and this paragraph exists so a reviewer does not expect the upward walk there and flag its absence.

WHY THE PREDICATE IS ITS OWN INCREMENT. It is the only part of the mechanism that changes what a currently-succeeding invocation REPORTS, whether by failing (the validator) or by withholding (the projections); it carries a known false positive (accepted cost (ii)); and it deliberately uses a DIFFERENT resolution from the default, so its review must check the lexical/canonical SPLIT rather than one rule. Its correctness property is also a negative ("must never pair..."), which the design pass showed is not established by passing the obvious tests: the anchor passed the first pass's own reproduction while leaving two further false passes standing.

WHY THE OMIT BEHAVIOUR LANDS IN INC2 AND NOT IN INC1, WHICH IS NOT WHERE IT FIRST LOOKS LIKE IT BELONGS. It is the projections' own behaviour, not the containment refusal, so inc1 is the natural first guess. The derivation forces inc2, for two reasons. FIRST, the omit is TRIGGERED BY THE CONTAINMENT PREDICATE and by nothing cheaper. Its scope is exactly the case that survives anchoring, an explicit `--metrics` naming a foreign log, and no lexical test separates that from an explicit `--metrics` naming the plan's own log spelled differently; A's guard exists because the lexical comparison gets the symlink case wrong. Putting the omit in inc1 therefore means putting the PREDICATE in inc1, which drags inc2's hardest review question (a negative property, established only by adversarial construction) forward into an increment whose question is a positive one, and leaves inc2 as a bool turned into a `problems.push`. SECOND, the three responses are only reviewable AGAINST EACH OTHER. The whole content of `Q-55-refusalscope` is that one predicate yields DIFFERENT answers on the validator and on the projections, so the defect to catch is a consumer wired to the wrong response, which is invisible unless they are read side by side. The same applies to accepted cost (ii): the symlinked-`docs/plans` false positive now has TWO manifestations, a loud false refusal in `validate` and a QUIET FALSE OMISSION in `status` and `next`, and those are not equally acceptable (a false omission in a surface an agent consumes withholds true evidence without saying anything is wrong with the tool), so the judgement has to be made over both at once or it is not made at all.

WHY THE SERIALISED REASONS LAND IN INC2 TOO, derived rather than assumed. The tempting framing is that this is the same predicate yielding a THIRD response, which would put it in inc2 by the argument above. That framing is wrong and the right one is stronger: the JSON reason is not a third response, it is the SECOND RENDERING of one response. The predicate yields two responses (refuse, omit), and the omit has two renderings (human text, JSON). Splitting the renderings across increments would mean inc2 COMPUTES a reason, prints it to text, and discards it for JSON, and a later increment re-surfaces a value that already existed, which is a deliberate half-done state across a boundary bought for nothing. Worse, it would ship a NEW behaviour with its explanation missing on exactly the surface the behaviour exists for: `Q-55-refusalscope` is about output an agent acts on, and an agent reads `--json`. That is a different and weaker position than the inc1-to-inc2 gap, which leaves an EXISTING defect open for one increment rather than shipping a new silence. Two mechanical reasons agree: the enums are consumed by the same code that computes the omission, and `status --json` has no golden test, so separating the JSON work would land the unguarded half of it with no co-located human-renderer behaviour to check it against and would force the acceptance check to rebuild the unsafe fixture a second time. One fixture answers both surfaces if they land together.

THE COST OF THAT PLACEMENT, STATED RATHER THAN HIDDEN. After inc1 alone, `next --source <foreign plan> --metrics <this repository's log>` STILL emits `state: converged` and `next: mark the step complete`. That is a known defect deliberately left open across an increment boundary, exactly as inc1 alone leaves defect A open by design, and it is the reason inc2 is not optional polish: inc2 closes the agent-facing half of defect C, which the design pass judged the more urgent half. WHY THE DOCUMENTATION HALF SHIPS WITH THE TIER POLICY AND NOT SEPARATELY. ## Risk classification

Each increment is argued on its own evidence. The first pass's "both risky" is NOT inherited; two of these arguments are new and the third has gained a factor it did not have.

`workflow-enforcement-tier-inc1` is RISKY (two consecutive clean rounds). It changes WHICH FILE the tool reads on every invocation of THREE commands that do not pass `--metrics`, plus which LEDGER two of them read, and the failure mode of a wrong anchor is not a crash but a confident wrong answer. The design pass measured that this failure mode IS SELF-CONCEALING: A's own build, correct on the reported reproduction, was still emitting `workflow invariants hold` at exit 0 on two other inputs until A attacked it deliberately, and nothing in the output distinguished the correct runs from the wrong ones. That is the same class of defect the increment exists to remove. It also COMPOUNDS FORWARD: after inc3 a mis-derived anchor stops being "reads the wrong file" and becomes "hard-fails a correctly instrumented project", so an inc1 defect escalates into a broken gate rather than staying a quiet one. The derivation additionally makes at least one SILENT JUDGEMENT CALL that no measurement settled (nearest-wins on a nested `docs/plans`), which is precisely the kind of thing a review round exists to catch. Relative-path handling is this tree's recorded weak spot rather than a neutral area: `is_safe_sidecar_ref` (`src/plan/source.rs:480-495`) exists because of it, and two backlog steps sit in the same family (`sidecar-ref-empty-string` order 63, `sidecar-ref-symlink` order 64). `workflow-enforcement-tier-inc3` is RISKY (two consecutive clean rounds).
